## Run locally

From the project directory:

```sh
nvm install
nvm use
npm ci
npm run local
```

The pinned runtime is Node.js 24.22.1. The local launcher creates `.env` from `.env.example` if needed, generates a private host token, starts the local database when necessary, builds the browser application, and starts the server. Open `http://localhost:3000` and sign in with `HOST_TOKEN` from `.env`. Keep that token stable to retain access to owned sessions and libraries. The host screen opens the library, creates a rehearsal session, or resumes a saved one.

The launcher uses native PostgreSQL on `127.0.0.1:55432`, with data under `.local/postgres`; PostgreSQL 14 is available on this machine. Set `PG_BIN` when the PostgreSQL binaries are elsewhere. `.env`, database files, and generated audio are local runtime data and are ignored by Git.

`compose.yaml` provides PostgreSQL 17.11 and the application with persistent database/audio volumes. Docker is unavailable in the current environment, so the Docker build and Compose path have not been verified. If you start only the Compose database and run the app on the host, include the matching `POSTGRES_PASSWORD` in both `DATABASE_URL` and `TEST_DATABASE_URL`; the passwordless defaults work with the native local database. The full Compose app already overrides its database URL with the configured password. The application applies the numbered SQL migrations at startup, recording them in `schema_migrations` under a database advisory lock.

For solo testing, open the director workspace, choose **Cast & lobby**, and click **Test as Rook**, **Test as Lark**, **Test as Quill**, or **Test as Pip**. Each link opens an independent player tab in the same browser and leaves real player invitations available. The director and character tabs retain their identities across refresh and navigation. These test seats use the actual session: their submissions become ordinary player input.

Copy player invites and the stage invite when the session is created; they are displayed once and redeemed once. Invited roles can also share one browser in separate tabs. Player/stage credentials last 12 hours; a credential-renewal and invite-reissue interface remains unfinished. A director can open the stage in the host browser and still receives the stage-only projection. Save reusable character cards with their traits, possessions, specialty, backstory, and private secret. Native version 1 JSON import/export is supported; external character-card formats are not. Exported definitions include private material.

Players can build their own cards before a show exists. Expand **Invite players to build characters**, enter a player label and any public character instructions, then choose **Create character link**. Share that private link with its intended player. Links last 30 days and can be shown again or revoked from the same panel. Each player can save unfinished progress, close the builder, and return using their link. Only that player's card and the instructions entered for them are available. Builder access remains separate from host and session access, including when testing several roles in one browser.

**Submit to director** validates the current form, adds one reusable card to the director's library, and makes that builder read-only. Use **Refresh player submissions** to load finished cards into the library and custom-show choices. Director approval and player readiness are still required in the show lobby. Send the separate player invitation after creating the show. Players can use AI Generate on their own character text fields. Suggestions use the current unsaved card, the director’s character instructions, and an optional player description. Pronouns require an explicit description. Generate and Apply leave saved progress unchanged; Save progress or Submit to director persists the card. Stop the local application and run `npm run local`, then refresh, to apply migration `005_character_builders.sql` and load the new routes.

Character and non-player character fields also use the current character's entered details, including unsaved edits, private notes, and recorded knowledge and relationships. ## Rehearse a scene

Open a conversation, have one player submit a question to Mara, and select that input in the director queue. Plan it, review and approve the classification, lock the input, draft the scene, review the script and proposed continuity, then publish. Repeat with a follow-up from another player. No other player needs to submit for either exchange.

For an action round, have the players submit intent and approach. The director reviews each outcome branch and any helpers/dependencies before locking and rolling. Regenerating or manually editing narration keeps those dice. Publication applies the saved effects and advances the appropriate counters. The stage and refreshed clients fetch the published state.

If generation fails, retry or use the manual narration/NPC dialogue controls. A restart exposes interrupted generation as failed and retryable; it retains accepted input and dice. The director can pause the table or abort an unfinished beat with a recorded reason. Between beats, use **Corrections** to append a public clarification and repair supported current state values.

## Direct the live world

In the director workspace, expand **Scene, characters & reveals** between beats. The session must be live or paused, with no unfinished beat. Every change needs a private reason and an acknowledgement that queued in-character dialogue and actions will be cancelled. Players can submit those words again for the changed situation; out-of-character questions remain queued.

**Change scene** chooses an existing destination or creates one, sets its public title and description, and selects which non-player characters move with the cast. Other present characters go offstage. Their identities, voices, sourced memories, and relationships persist. New custom shows retain all authored locations. Older sessions recover only the current location and existing character locations under neutral labels; add other destinations as needed.

**Create or edit character** changes a non-player character's profile and presence. Recorded knowledge and relationships remain intact. **Reveal a secret** selects a private source and requires separate public wording. That wording appears under **Known to the party** for players, director, and stage. Only the selected witnesses physically present in the scene gain the corresponding sourced memory. Raw secrets and reveal conditions stay private; revealing an identity does not automatically change the public name.

These operations preserve published dialogue, dice, effects, and cached audio. They do not correct past rulings or rewrite the transcript. Successful saves close their form; failures retain unfinished words, and another director's changes require an explicit reload before saving.

**Corrections** references any published beat and adds an explicit public note. It can also replace an existing public fact, set character strain, or set a public track value. Review the before/after preview and choose whether each existing factual NPC memory should be corrected or retained as a belief. Uninformed characters gain no knowledge. A text-only clarification is valid. Corrections require a private reason and acknowledgement that pending in-character input will be cancelled; they preserve original publications, dice, recordings, and beat/round counters. Setting a countdown value does not trigger its completion effects. The public correction ledger remains visible for older beats outside the recent transcript window.

**Private AI direction** applies only to the active beat and is sent to the AI with the next plan or render. Saving before lock clears the plan and requires fresh stakes review. Saving after lock clears the script and continuity review while preserving locked input and dice. Saving also discards unsaved script or stakes edits. Save and Clear are explicit; another director's revision preserves unsaved direction until **Reload saved direction**. New beats start with empty direction. Stored direction is excluded from public snapshots and is never sent directly to speech synthesis; the director must still review generated text before publication.

# Codex kickoff: Twitch AI Roleplay Engine

## Use

## Prompt

Read `docs/PROJECT_PLAN.md` (or the attached `PROJECT_PLAN.md`) completely before proposing the application design. It is the product, gameplay, and reliability specification for a Twitch multiplayer AI roleplay engine.

The distinguishing feature is a shared live show with real player-to-NPC conversations, not merely AI descriptions of submitted actions. Preserve all of these:

- Short conversation beats that do not wait for the whole party, plus coordinated action rounds that can include dice.
- Third-person narration interleaved with attributed, direct NPC dialogue.
- Tracked NPC identities, voice profiles, relationships, knowledge, beliefs, secrets, and event-backed continuity.
- Player control of their own dialogue and choices. AI must not invent player-character speech.
- A human Sub-DM who reviews stakes and drafts before public publication.
- Server-generated 2d6 checks, immutable results, deterministic approved effects, and no rerolls when narration or TTS is retried.
- One canonical session history, reusable scenarios and character cards, optional player audio, and a separate OBS stage.
- Persistence, role-filtered data, reconnect recovery, and a usable manual fallback.

Start by inspecting the repository if one exists. Respect its conventions where compatible with the plan. Do not assume that an old Twitch bot, prior roleplay app, or provider integration is available.

This task is **design first**. Produce:

1. `docs/ARCHITECTURE.md`: application boundaries, domain types, persistence, state machines, commands/events, permissions, AI/TTS adapters, transaction boundaries, and recovery.
2. `docs/IMPLEMENTATION_PLAN.md`: small milestones, affected modules, dependencies, and concrete acceptance tests mapped to the plan's test IDs.
3. Short decision records under `docs/decisions/` for material choices, including supported dependency versions and any deviations from the defaults.
4. Player, director, lobby, and stage UX flows or low-fidelity wireframes. Include conversation, follow-up, action, stakes review, script review, playback, errors, and reconnect states.

Use the proposed Vue/TypeScript, Node/Fastify, Socket.IO, PostgreSQL, and Zod stack unless repository evidence or a specific trade-off justifies a change. Verify current supported versions and provider capabilities. Do not choose a model or voice by guessing availability, and do not add infrastructure merely for hypothetical future scale.

Record reasonable defaults for non-blocking unknowns. Clearly identify genuine conflicts and product decisions. Do not silently simplify the application into a generic chat room, drop tracked NPC conversation, or move all authority into an AI prompt.

The first implementation slice, when implementation is requested, must demonstrate four-player participation, a two-beat conversation with a recurring NPC, a reviewed action contract and dice outcome, a public stage, and refresh-safe state using fake providers before relying on live APIs.

Finish this design task with a summary of the proposed architecture, the smallest playable slice, unresolved risks, and the exact files produced. Do not build or deploy the full application during this initial task.
